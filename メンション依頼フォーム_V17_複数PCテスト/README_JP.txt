メンション依頼フォーム v26｜V17 会社実環境・複数PC同時テスト
==============================================================

■ V17の目的
これまでのV8～V16で単一PC・ローカル環境の耐久性を確認しました。

V17では、実際の会社共有フォルダ上で
複数の物理PCが同じCSVへほぼ同時に書き込み、

・SMB共有上でも FileShare.None のロックが効くか
・複数PCの同時書込みでも欠損しないか
・同一RequestIDを複数PCから処理しても重複しないか
・Pendingが各PCで正常に削除されるか

を少量データで確認します。

負荷試験ではありません。
2～5台程度、1台あたり3 Pending程度からの実施を推奨します。


==============================================================
■ まずローカル1台で試す
==============================================================

START_LOCAL_SIMULATION.cmd

を実行してください。

複数の仮想参加者を1台のPC上で起動し、
READY → 一斉START → CSV書込み → 集計
までV17の流れを練習できます。

正常終了時：
RESULT : PASS_LOCAL_SIM

となります。

重要：
PASS_LOCAL_SIM はV17の仕組みが1台で正常に動いたという意味です。
実際のSMB・複数PC間ロックを確認したことにはなりません。


==============================================================
■ 会社で複数PCテストする
==============================================================

【事前準備】
同じV17 ZIPを各PCへコピーし、
各PCのローカルで展開してください。

V17自体を共有フォルダから直接実行する必要はありません。

共有側には、テスト専用の親フォルダを1つ用意してください。
UNCパス推奨です。

例：
\\server\share\MentionTest

V17はその配下に自動で

MentionRequest_V17_MultiPC_Test

という専用フォルダを作ります。

本番の「書き込み用」CSVを直接使用しません。


【代表者PC】
START_HOST.cmd

1. 共有テスト用の親フォルダを入力
2. 参加PC数を入力
3. シナリオを選択
4. 1台あたりPending数を入力
5. 1 Pending内の依頼数を入力

Session IDが表示されます。

代表者は画面を開いたまま待機してください。


【参加者PC】
START_PARTICIPANT.cmd

1. 代表者と同じ共有親フォルダを入力
2. Session IDを入力
3. Participant IDを入力

Participant ID例：
PC01
PC02
PC03

同じIDを2台で使わないでください。

参加者はREADY状態で待機します。
全員READYになると代表者PCからSTART信号が作成され、
各PCがほぼ同時にWorkerを開始します。


==============================================================
■ シナリオ
==============================================================

1 UNIQUE
全PCが別々のRequestIDを送ります。

確認：
全件SUCCESS
欠損0
重複0


2 DUPLICATE
全PCがまったく同じRequestIDを同時処理します。

確認：
1つだけSUCCESS
残りはDUPLICATE_SKIP
CSVには1セットだけ存在
重複0

複数PC間での冪等性確認として特に重要です。


3 MIXED
奇数番号のPending：
全PC共通RequestID

偶数番号のPending：
PCごとに別RequestID

UNIQUEとDUPLICATEを同時に発生させます。

会社での最終確認にはMIXEDを推奨します。


==============================================================
■ 推奨初回設定
==============================================================

参加PC              : 3台
Scenario            : MIXED
Pending / PC        : 3
Requests / Pending  : 3

この場合でもデータ量は非常に小さく、
大規模な負荷試験にはなりません。


==============================================================
■ 結果
==============================================================

複数物理PCから正常に完了すると：

RESULT : PASS

ローカル1台模擬なら：

RESULT : PASS_LOCAL_SIM

MULTI_PCを選んだのに参加したPC名が1種類だけの場合：

RESULT : CHECK_SINGLE_MACHINE_ONLY

として、複数PC検証済みとは扱いません。


主な確認項目：
SUCCESS
DUPLICATE_SKIP
RETRY total
Pending remaining
Expected CSV rows
Actual V17 CSV rows
Missing keys
CSV duplicate rows
Lock file remaining
Unique machine names


==============================================================
■ 安全性
==============================================================

・本番CSVは使用しません
・実Desktop\MentionRequest_Pendingは使用しません
・V17専用共有フォルダだけを使用します
・各PCのテストPendingはV17パッケージ配下の local_results に作成
・.ps1ファイルは使用しません
・ExecutionPolicyを変更しません
・ExecutionPolicy Bypassを使用しません
・Workerの書込み／ロック／重複判定はV16までで使ったv26相当ロジック
・Worker再試行上限は300秒のままです


==============================================================
■ 注意
==============================================================

V17は「少量の実環境確認」です。
会社共有サーバーに負荷をかけることを目的としていません。

最初は2～3台 × 1～3 Pending程度で確認し、
問題なければ3～5台程度まで増やす運用がおすすめです。

共有テスト親フォルダへの作成・書込み・削除権限が
参加者全員にあることを事前に確認してください。


==============================================================
■ V17.1 修正（ローカルCHECK対策）
==============================================================

初版V17では、古いWindows Script Host/JScript環境で
Date.toISOString() が利用できない場合、
Worker処理自体は成功していても participant report が生成されず、
最終結果が CHECK になることがありました。

V17.1では：
・Date.toISOString() を使用しない日時生成へ変更
・古いJScript環境向けに集計処理を互換化
・participant report生成に失敗した場合はDONEを作らない
・集計失敗を正常完了と誤認しない

ように修正しています。

2026-09-06 ローカル初版テストでは、
CSV 240/240行、欠損0、重複0、lock残存なしまで正常で、
CHECK原因はparticipant report 0件のみでした。
